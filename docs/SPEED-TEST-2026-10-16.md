## 1. Вердикт

Поезд J ничего не просадил: хабы вакансий 91-93 mobile и 97-100 desktop, LCP 3.2-3.3 с, то есть на уровне остальных внутренних страниц; блок 12 карточек добавил только RSC-префетчи ссылок (гео-хаб: 77 запросов вместо ~45, +0.2 МБ), на score это не влияет. Слабые места две: главная на мобиле (81, LCP 4.2 с при FCP 1.9 с, то есть крупный элемент героя отрисовывается поздно) и TBT на десктопе главных RU/UK (350-370 мс) плюс индекс блога (TBT 230-270 мс, вес 0.93 МБ из-за шести обложек) - всё это главный shared-чанк `44o2227` с JS-исполнением 1.1-1.9 с. Полевые CrUX-данные сегодня снять не удалось технически: у ключа MCP выключен Chrome UX Report API (проект 757316827235), а бесключевая квота PSI исчерпана; для молодого сайта с нашим трафиком в CrUX по большинству URL данных скорее всего и нет, так что Google судит нас не по полю, а по факту пригодности страниц (лаборатория зелёная).

## 4. План фиксов

### П1 - дёшево (эффект на каждый вложенный час)

1. **Убрать legacy-полифилы из главного чанка.** Lighthouse на каждой странице показывает 13.8 КБ лишних полифилов в `44o2227_5arws.js`. Фикс: `browserslist` в package.json на современные таргеты (Baseline). Выигрыш: минус 14 КБ на каждой странице, чуть меньше parse-времени, по пункту score там, где TBT на грани.
2. **prefetch={false} на каталоге 12 карточек и городских ссылках гео-хаба** (`app/[locale]/vacancies/page.tsx`, блок поезда J; паттерн уже применён в `components/HomePage.tsx:212-235`). Сейчас гео-хаб тянет 54 RSC-префетча на 0.24 МБ. Выигрыш: минус ~35 запросов и ~0.15 МБ мобильного трафика девушки; score не изменится, но idle-сеть и батарея скажут спасибо.
3. **Обложки на индексе блога: сузить sizes для карточек** в `components/seo/BlogCoverImage.tsx` (variant="card"). Сейчас карточки грузят w=750 (38-77 КБ каждая, суммарно 0.30 МБ); на мобиле карточка рендерится ~в 2 раза уже. Качество q90 НЕ трогаем (см. П3). Выигрыш: минус ~0.12-0.15 МБ на /blog, Speed Index -0.3-0.5 с, score 84 -> ~88.
4. **Проверить отложенную инициализацию тяжёлых секций главной** (three.js `LogoMark3D`, GSAP-сцены ниже первого экрана): монтирование через next/dynamic + IntersectionObserver, а не на общей гидрации. Диагноз: JS-исполнение 1954 мс на десктопе, 1125 мс в одном чанке, TBT 370 мс. Выигрыш: TBT desktop -150-250 мс, главные RU/UK 82-83 -> ~90+ desktop.

### П2 - дороже (отдельное решение)

1. **Разбор shared-чанка `44o2227` бандл-анализатором** и вынос GSAP/motion из критического пути всех страниц (он грузится даже на текстовых вакансиях). Потенциал: -300 мс TBT на главных и блог-индексе, +3-5 пунктов mobile главной. Стоимость: полдня аккуратной работы + регресс-тест анимаций.
2. **LCP главной на мобиле (4.2 с).** Разрыв FCP 1.9 -> LCP 4.2 означает позднюю отрисовку крупного элемента героя (вход заголовка стартует после динамического импорта GSAP, строки начинают с blur(7px) и смещения, `components/hero/HeroSection.tsx:87-124`). Шаг 1: вытащить LCP-элемент из full-отчёта. Шаг 2: если это заголовок, на мобиле отдавать первый кадр без blur (анимировать только второстепенные элементы). Потенциал: LCP -1.0-1.5 с, mobile 81 -> ~90. Трогает витринную анимацию героя, поэтому только после «да» владельца с макетом до/после.
3. **Ревизия шрифтов**: 6 woff2 на 0.11 МБ; если какое-то начертание живёт только в декоре, убрать. Потенциал скромный: FCP -0.1 с.

### П3 - не делаем и почему

1. **СЕО-скелет не трогаем** (hreflang, canonical, sitemap, URL, JSON-LD) - прямой запрет CLAUDE.md; ни один фикс выше его не задевает.
2. **Обложки не пережимаем ниже q90**: q75 даёт бандинг на тёмных неоновых градиентах (осознанное решение, комментарий в `BlogCoverImage.tsx`); фирменный вид дороже 30% веса картинок.
3. **Видео и постеры не трогаем**: mp4 не грузится до клика, постер 46.8 КБ уже меньше, чем выдал бы оптимизатор Next. Выигрыша нет, риск сломать принятый владельцем формат есть.
4. **3D/GSAP-герой не выпиливаем ради score**: это витрина агентства и конверсия; 81/82 на главной не блокируют ни индексацию, ни ранжирование. Корректируем только подачу первого кадра (П2.2) с согласия владельца.
5. **За 100/100 на мобиле не гонимся**: последние пункты стоят дороже всего и покупаются отказом от того, что продаёт.

## 5. Влияет ли это на SEO (честно)

Core Web Vitals - слабый фактор ранжирования, скорее tie-breaker при прочих равных; контент, интент и ссылки весят на порядок больше. Google оценивает не лабораторный score, а полевые данные CrUX реальных пользователей Chrome, и по большинству наших URL их при нашем трафике скорее всего недостаточно (сегодня проверить поле не удалось: у ключа отключён CrUX API + исчерпана квота; стоит включить Chrome UX Report API в консоли проекта ключа). Практический вывод: штрафа за скорость у нас нет и не предвидится, все страницы зелёные или около того; главный выигрыш от фиксов - UX и конверсия (девушка с телефона на медленной сети быстрее видит первый экран и доходит до анкеты), плюс лёгкие страницы и сервер за 1 мс помогают краулингу. ## Дополнение: П2.2 hero-LCP + П2.3 шрифты - диагностика и фикс на localhost (16.10 ночь, НЕ закоммичено)

Среда: прод-сборка на localhost:3111, Lighthouse 13 (симуляция как PSI) + DevTools-трейсы (Moto G 412px, Slow 4G, 4x CPU, холодный кэш). Сырьё: scratchpad сессии f6b7b501, папка speed-p2.

### Что показала диагностика ревила героя

- LCP-элемент главной на мобиле = span «OnlyFans» (hero-accent-shimmer) внутри h1 - подтверждено трейсом (nodeId в LCPBreakdown, size 76327px²).
- Гипотеза «заголовок скрыт до гидратации GSAP» на мобиле НЕ подтвердилась: CSS-гейт `.hero-pending [data-hero-reveal]` действует только с 768px (десктоп), на телефоне текст виден прямо в SSR-HTML, а GSAP на мобиле вообще не грузится (гейт + lazy-import уже в проде с волны perf-коммитов fc436e9/de749a2, комментарий в globals.css:154). В каждом трейсе LCP == FCP == первый paint страницы вообще: элемент рисуется в первый же возможный кадр, раньше нечего ускорять скрытием/показом.
- Реальная причина позднего первого кадра: один длинный таск парсинга (~1.85 с при 4x CPU: 710 КБ HTML с 43 инлайн self.__next_f чанками + инлайн-CSS) и 5 проходов layout до первого кадра (166 мс без троттлинга), из них минимум два - перелейауты от шрифтов, приезжающих ПОСЛЕ первой компоновки. Парсинг/JS-граф - это зона П2.1 (разбор shared-чанка), шрифтовые перелейауты - лечатся П2.3 ниже.
- Механику ревила НЕ трогали (осознанно): на десктопе прятать до первой отрисовки - единственный паттерн без вспышки «виден - исчез - снова появился» (GSAP приезжает лениво через секунды после гидратации, любой вариант «SSR видим + скрыть при старте анимации» даёт именно эту вспышку); десктопный LCP и так 0.9 с. Мобила уже открыта с первого кадра. Визуал не изменился ни на пиксель.

### Фикс шрифтов (app/[locale]/layout.tsx)

У playfair-rest заменено subsets ['latin'] -> ['cyrillic'] + preload: true. У next/font subsets управляет ТОЛЬКО прелоадом (@font-face эмитятся для всех сабсетов всегда - проверено по инлайн-CSS сборки), поэтому единственное изменение в выдаче - четвёртый `<link rel=preload>` на 12 КБ кириллический Playfair normal (cd9d619e...), которым набраны h1 line1 («Работа моделью» / «Робота моделлю») и все serif-заголовки ru/uk. Раньше этот файл обнаруживался только из CSS после первого layout (старт ~1.1 с на 4G, финиш ~2.3 с) и давал поздний swap + перелейаут; теперь он стартует вместе с остальными прелоадами (~0.6 с) и успевает до первого кадра. Латинский normal (22.5 КБ, ниже первого экрана) и кириллический italic (13 КБ, ниже первого экрана) сознательно НЕ прелоадятся - урок «прелоад 4 вариантов Playfair крал полосу 4G и ронял LCP» остаётся в силе. Хэши файлов не изменились - дублей загрузки нет, начертания те же, визуал идентичен. Цена: en/es страницы прелоадят эти 12 КБ вхолостую (приоритет ru/uk = 74% мобильного трафика). font-display: swap у всех 30 @font-face - проверено.
