## Исправлено и на проде

### 1. Ротация дат вакансий — повтор нарушения, которое уже закрывали

`components/seo/StructuredData.tsx:215` — `JobPosting.datePosted` был привязан
к `post.updatedAt`. Любая SEO-правка текста статьи омолаживала дату вакансии:
6 статей × 4 локали = до 24 документов с фальшивой датой без единого изменения
в самой вакансии.

Это дословно то, ради чего 28.07 был обезврежен `scripts/rotate-vacancies.mjs`.
Скрипт выключили — живой источник той же проблемы остался в коде и работал.
Теперь только `publishedAt`. Менять его можно ТОЛЬКО при реальном изменении условий.

### 2. Дубли JobPosting: одна вакансия на шести URL

Замер на проде до правки:

| URL | Заголовок вакансии |
|---|---|
| `/blog/rabota-modelyu-onlyfans` | Модель OnlyFans (удалённо, без опыта) |
| `/join` | Модель OnlyFans (удалённая работа) |
| `/vacancies/model/ukraine` | Онлифанс работа моделью в Украине |
| `/vacancies/for-girls` | Работа для девушек онлайн |
| `/blog/onlyfans-rabota-kiev` ↔ `/vacancies/model/ukraine/kyiv` | одна вакансия, два URL |
| то же для Львова и Харькова | |

Google называет это duplicate job postings и прямо запрещает. Санкция по
job-policies бьёт по домену целиком.

**Проведена граница: блог — информационные статьи, вакансии живут в `/vacancies`
и `/join`.** Разметка удалена из блога вместе с `JOB_TITLE`, `CITY_JOB_TITLE`
и `jobPostingProps`. Городские вакансии остались на `/vacancies/model/ukraine/{city}`.

Одесса и Днепр гео-страниц не имеют. Если они нужны как вакансии — заводим
гео-страницу в `lib/content/model-geo/countries/`, а не размечаем блог-статью.

Потеря нулевая: Google for Jobs в украинской adult-выдаче не отдаётся вовсе
(проверено 28.07) — rich-результата мы не получали, только несли риск.

### 3. Вторая сущность бренда на всех 266 страницах

`ProfessionalService` объявлял второе «OFM's Model Agency» без `@id` — Google
видел две разные компании с одним названием. Плюс это подтип `LocalBusiness`,
которому обязателен `address`; физического адреса нет и публиковать его мы не будем.

Удалён. Услуги перенесены в `Organization` через `makesOffer` → `Service`
(`Service` — не `LocalBusiness`, адрес не нужен), привязанный к `#organization`.
На проде: `ProfessionalService` 0, `Organization` ровно 1 на страницу.

### 4. Слово «контракт» в сниппетах Google

`messages/en.json`, `messages/es.json` (×2), `lib/content/blog/posts/safety.ts` —
упоминание контрактов и договоров в meta description. Показывалось в выдаче,
противореча модели «договоров нет». Заменено.

### 5. Блок «Читайте также» работал против цели

`lib/content/blog/index.ts` — статьи отбирались только по `publishedAt`, то есть
ссылки получали самые свежие материалы, а не самые ценные. 62% рециркуляции блога
уходило шести случайным по дате статьям; пиллар с 9 963 показами получал 3 ссылки
из 252.

Введён `PILLAR_SLUGS`: один слот из трёх резервируется под пиллар. Выбор
детерминированный, но разный для разных статей-доноров — иначе получился бы новый
перекос вместо старого. Сверять список с GSC раз в квартал.

### 6. Логотип не проходил порог Google

`components/JsonLd.tsx` — `Organization.logo` вёл на `/icon.svg`, который объявляет
`width="32" height="32"` при минимуме Google 112×112. Логотип не попадал в брендовый
блок выдачи. Переключён на `/icon.png` (512×512, уже был на проде), `image` — на
`/og-default.png` (1200×630).

### 7. Пиллар в sitewide-слоте

Футер отдавал 71 ссылку с каждой страницы локали статьям с 7–30 показами, а
страница с 9 963 показами не получала ни одной sitewide-ссылки. Пиллар добавлен,
ключ `footer.pillarWhatIs` заведён в 4 локалях.

### 8. Карточки ленты вакансий размечены как h3

18 позиций на `/vacancies/model` рендерились обычными ссылками в `div`. Google видел
не листинг вакансий, а абзац со ссылками. Лидер кластера xjobber держит позицию 1
с 34 карточками как H3 и 114 внутренними ссылками. После правки на
`/uk/vacancies/model`: **33 h3 и 134 внутренние ссылки**.

### Переключатель локалей — проверено вживую, регрессии нет

Серверная разметка со статьи блога ведёт на витрину локали (`/uk/blog`), потому
что клиент не знает доступность переводов без 1,7 МБ контента в бандле, а
непереведённых пар «локаль + slug» сорок — ссылка на 404 хуже кнопки.
При открытии меню ссылки апгрейдятся до точного перевода из hreflang-тегов
страницы. Замер в браузере на `/blog/chto-takoe-onlyfans`:

```
до:    uk → /uk/blog                      en → /en/blog        es → /es/blog
после: uk → /uk/blog/chto-takoe-onlyfans  en → /en/blog/...    es → /es/blog
```

Испанская осталась витриной — этой статьи в `es` нет, и в hreflang её тоже нет.
Ссылка на 404 не возникает ни при каком сценарии.

## Историческая справка: как это выглядело до правки

### hreflang в HTTP-заголовке противоречит HTML

`i18n/routing.ts` — нужна одна строка `alternateLinks: false`.

Замер на проде, `/blog/onlyfans-rabota-kiev`:

```
HTTP Link  → ru, uk, en, es, x-default      ← /en/ и /es/ отдают 404
HTML link  → ru, uk, ru-UA, uk-UA, x-default ← корректно, только живые локали
```

next-intl добавляет заголовок `Link` со всеми четырьмя локалями для ЛЮБОГО пути —
он не знает, какие страницы существуют. Переведены не все: в блоге uk 42, en 24,
es 20, то есть около 40 битых целей hreflang.

HTML-разметка формируется нами в `lib/i18n/paths.ts`, она полная и корректная.
Google принимает hreflang из HTML-тегов, HTTP-заголовков или sitemap — достаточно
одного источника. Заголовок ничего не добавляет, только противоречит.

Правка не трогает HTML-разметку, canonical, структуру URL и роутинг — только
выключает лишний заголовок.
